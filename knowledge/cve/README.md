# knowledge/cve — the committed CVE snapshot

**Class:** data  **Refreshed by:** `.github/workflows/cve-snapshot.yml` every 6h

`snapshot.json` is a pruned, merged view of six public vulnerability feeds, kept
in git so an engagement has recent CVE data on its first run and with no
network. It is the *floor*, not the source of truth: `scripts/cvefeed` tries a
live refresh first and only falls back here, printing the snapshot's age every
single time it does.

The methodology this data serves is
[`../techniques/cve-triage-2026.md`](../techniques/cve-triage-2026.md).

## Files

| File | What it is |
|---|---|
| `snapshot.json` | the committed data set, regenerated by CI, never hand-edited |
| `selftest-fixture.json` | five hand-written records for `scripts/cvefeed --selftest`; deliberately stale, not live data, never read it for triage |

## Feeds and how each one is fetched

| Feed | Host | What it contributes | How it is fetched |
|---|---|---|---|
| CISA KEV | `www.cisa.gov` | `kev`, `kev_date_added`, `ransomware` — **proven in-the-wild exploitation** | whole catalog JSON, then filtered to additions inside `kev_window_days` |
| EPSS (FIRST) | `api.first.org` | `epss`, `epss_date` — predicted exploitation in 30 days | batched 100 CVE ids per request, only for ids already in the set (the full EPSS file is 20MB+) |
| NVD 2.0 | `services.nvd.nist.gov` | title, CVSS, CWE, CPE version ranges, references | `pubStartDate`/`pubEndDate` window chunked to NVD's 120-day maximum, `cvssV3Severity=CRITICAL` then `HIGH`, paged 2000 at a time. `NVD_API_KEY` is honored; without one it backs off through the 403/429s |
| nuclei-templates | `raw.githubusercontent.com` | `nuclei_template` — **a non-destructive check already exists** | the repo's `cves.json` (one JSON object per line), reduced to a CVE → template-path map |
| GHSA | `api.github.com` | package-level advisories with `vulnerable_version_range` | reviewed advisories in the window, high + critical. **Needs a token, so it is fetched only in CI** and baked in; at engagement time `cvefeed` says `ghsa: skipped (no token)` rather than failing |
| OSV | `api.osv.dev` | ecosystem ranges, and `MAL-*` compromised-package advisories | one POST per catalogued package (`scripts/cvefeed products`); OSV's huge `versions` arrays are dropped and only ranges kept |

A record that several feeds describe is merged into one entry keyed by its CVE
id (or the GHSA/MAL id when there is no CVE), and every feed that touched it
leaves a `provenance` row. That is how a consumer tells a KEV-confirmed
exploited CVE from an EPSS guess: `kev: true` can only come from the KEV feed.

## Pruning policy

A snapshot that holds every CVE is a snapshot nobody commits. A record is kept
only if it is

- on CISA KEV, with its addition inside `kev_window_days` (default 365), **or**
- a `MAL-*` malicious-package advisory (always kept, any age), **or**
- published inside `window_days` (default 30) **and** either `cvss >= min_cvss`
  (7.0), `epss >= min_epss` (0.05), or a nuclei template exists for it.

Descriptions are dropped, titles capped at 200 characters, references at 6 per
record, affected ranges at 12. The nuclei map is pruned to the CVEs that
survived. Current size: roughly 1 MB and ~850 records, sorted by id so the CI
diff is readable. If it grows past a couple of megabytes, tighten
`--window-days` rather than letting the repo carry it.

## Schema

```jsonc
{
  "schema": 1,
  "generated_at": "2026-11-13T22:35:18Z",     // when CI (or your refresh) built it
  "policy": {"window_days": 30, "kev_window_days": 365,
             "min_cvss": 7.0, "min_epss": 0.05},
  "sources": {                                 // one entry per feed
    "kev": {"status": "ok",                    // "ok" | "partial: ..." | "failed: ..." | "skipped: ..."
            "records": 322, "url": "...", "fetched_at": "...", "note": "..."}
  },
  "nuclei": {"CVE-2026-33017": "http/cves/2026/CVE-2026-33017.yaml"},
  "records": [{
    "id": "CVE-2026-33017",                    // CVE id, else the GHSA/MAL id
    "title": "...", "published": "...",
    "severity": "CRITICAL", "cvss": 9.8, "cwes": ["CWE-94"],
    "kev": true, "kev_date_added": "2026-10-30", "ransomware": false,
    "malicious_package": false,                // true only for MAL-*
    "epss": 0.964, "epss_date": "2026-11-12",
    "nuclei_template": "http/cves/2026/CVE-2026-33017.yaml",
    "affected": [{"package": "pypi/langflow",  // "ecosystem/name" or "vendor:product" from a CPE
                  "introduced": "0", "fixed": "1.9.0",
                  "last_affected": null,
                  "raw": ">= 1.0, < 1.9.0",    // GHSA/CPE constraint text, when there is one
                  "source": "osv"}],
    "product_hints": ["langflow", "pypi/langflow"],   // what match() searches
    "references": ["..."], "poc_refs": ["..."],
    "provenance": [{"feed": "kev", "upstream_id": "CVE-2026-33017",
                    "fetched_at": "2026-11-13T22:33:02Z"}]
  }]
}
```

`scripts/cvefeed match --json` emits a different, derived document — the
`cve-candidates.json` that recon writes and the planner reads. It wraps each
record with `match_confidence` (`exact` | `banner` | `range-unknown` |
`product-only`), `match_reason`, the `why` line, a `data` block carrying the
age and provenance of the data set it came from, an `excluded_by_version` list,
and the `disclaimer`.

## Refreshing it

```
scripts/cvefeed status                        # how old is what I have, and from where
scripts/cvefeed refresh                       # refresh the local cache (engagement path)
scripts/cvefeed refresh --out knowledge/cve   # rewrite this snapshot (what CI runs)
```

CI runs the second form every 6 hours and commits only when the file changed.
Nothing else should write `snapshot.json`: at engagement time `cvefeed` writes
to a cache outside the repo (`$MYTHOS_CVE_CACHE`, else
`$XDG_CACHE_HOME/mythos/cve`), because the repo may be mounted read-only.

## Honest limits

- **A KEV entry means a vulnerability was exploited in the wild somewhere. It
  does not mean this target is vulnerable, or that it is exploitable from where
  you stand.**
- **EPSS is a prediction**, not evidence. A 0.97 means models expect
  exploitation; a 0.001 does not mean safe.
- A version match is worth exactly as much as the fingerprint behind it.
  `exact` means a version read off the product itself fell inside a published
  range; `banner` means the version came from a header or a guess; and
  `range-unknown` means nobody could check the version at all. None of the
  three is a finding.
- The affected ranges come from NVD CPEs, GHSA and OSV, which disagree with
  each other and with vendors, and are frequently incomplete. A record ruled
  out "by version" can still be exploitable — that is why `cvefeed` prints the
  ruled-out list instead of hiding it.
- Pruning means **absence here is not absence in the world**: anything older
  than the window, below the score floor and not on KEV was never fetched.
- CVE coverage of the AI/automation stack in `scripts/cvefeed products` is
  patchy. Several of those projects ship fixes without filing CVEs at all, so
  the lack of a candidate for Dify or ComfyUI says little.
- Backfilling: EPSS scores move daily and KEV additions land on business days,
  so two snapshots a day apart will rank the same CVEs differently. That is the
  data moving, not a bug.
